# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Firmware for a DMM (digital multimeter), currently in early bring-up: `Core/Src/main.c` is still essentially the STM32CubeMX-generated skeleton (HAL init, 64 MHz HSI clock, GPIO, BSP LEDs and VCP UART). The target is an **STM32H753ZIT6 on a NUCLEO-H753ZI (Nucleo-144) board**, generated by STM32CubeMX 6.15.0 with STM32Cube FW_H7 V1.12.1, built with STM32CubeIDE 1.19.0 (GNU Tools for STM32 13.3).

## Build

This is an Eclipse/CDT managed-build project (`.project`/`.cproject`); there is no Makefile or CMake file in the repo. The makefiles are generated into `Debug/` or `Release/` (both gitignored) when the IDE builds. Configurations: `Debug` and `Release`, both at `-Os`.

Headless build from the command line (the toolchain is not on PATH; it ships inside CubeIDE at `C:\ST\STM32CubeIDE_1.19.0\STM32CubeIDE`):

```
"C:\ST\STM32CubeIDE_1.19.0\STM32CubeIDE\headless-build.bat" -data "C:\Users\NoelBoyd\STM32CubeIDE\dmm_workspace" -import "C:\Users\NoelBoyd\STM32CubeIDE\dmm_workspace\DMM-FIRMWARE" -build DMM-FIRMWARE/Debug
```

Output is `Debug/DMM-FIRMWARE.elf`. Flashing and debugging are done from STM32CubeIDE over the on-board ST-LINK. There are no unit tests.

Static analysis: cppcheck is installed (`C:\Program Files\Cppcheck`); its reports (`cppcheck_*.txt`) are gitignored. Point it at `Core/` with the same defines and include paths the build uses (below), not at `Drivers/`.

Compiler defines: `USE_HAL_DRIVER`, `STM32H753xx`, `USE_PWR_LDO_SUPPLY`, `USE_NUCLEO_64`, `DEBUG` (Debug only). Include paths: `Core/Inc`, `Drivers/STM32H7xx_HAL_Driver/Inc` (+ `Inc/Legacy`), `Drivers/CMSIS/Device/ST/STM32H7xx/Include`, `Drivers/CMSIS/Include`, `Drivers/BSP/STM32H7xx_Nucleo`. The BSP board selection actually comes from `Core/Inc/stm32h7xx_nucleo_conf.h` (`USE_NUCLEO_144`, `USE_NUCLEO_H753ZI`), despite the `USE_NUCLEO_64` project define.

## CubeMX code generation (important)

`DMM-FIRMWARE.ioc` is the source of truth for pinout, clocks, NVIC and peripheral init. Regenerating from it rewrites `Core/Src/main.c`, `stm32h7xx_it.c`, `stm32h7xx_hal_msp.c`, the headers in `Core/Inc`, the linker scripts and `Drivers/`.

- In any CubeMX-generated file, put custom code **only** between `/* USER CODE BEGIN ... */` and `/* USER CODE END ... */` markers; anything outside them is lost on regeneration (`KeepUserCode=true`).
- Prefer putting application logic in new files under `Core/Src` / `Core/Inc` and calling it from the USER CODE sections of `main.c`.
- Don't hand-edit peripheral init (`MX_*_Init`, `SystemClock_Config`, `HAL_*_MspInit`) to change hardware config. Change the `.ioc` in CubeMX and regenerate, or the next regeneration will undo it.
- Treat `Drivers/` (HAL, CMSIS, BSP) as vendor code: don't modify it.
- Commit before regenerating from the `.ioc` so you can diff what CubeMX changed.

## Hardware/runtime notes

- Clock: SYSCLK = HSI 64 MHz, PLL off, VOS scale 2, flash latency 1, all buses /1.
- I-cache and D-cache are **disabled** and the MPU is not configured. If caches are enabled later, DMA buffers need cache maintenance or placement in a non-cacheable MPU region.
- Linker (`STM32H753ZITX_FLASH.ld`): code in 2 MB flash; `.data`/`.bss`/heap/stack in AXI SRAM `RAM_D1` (0x24000000, 512K). DTCM, ITCM, `RAM_D2` and `RAM_D3` are defined but unused. Note that some DMA controllers cannot reach DTCM. Heap 0x200, stack 0x400 (set in the `.ioc`).
- Peripherals so far: user button B1 (PC13), LEDs LD1–3 via BSP (`BSP_LED_*`), and COM1 = USART3 on PD8/PD9 → ST-LINK virtual COM port at 115200 8N1. `USE_COM_LOG=1` in `stm32h7xx_nucleo_conf.h`, so `printf` is retargeted to COM1.
- NVIC priority group 4 (all preemption bits).

## Coding conventions

From `Docs/best-practices.md`:
- Use HAL consistently. Don't mix HAL, LL and direct register access in the same file.
- Use `<stdint.h>` fixed-width types, `volatile` for ISR-shared and hardware-mapped data, and `const` for lookup tables and config. Use `enum`/`const`/`#define` instead of magic numbers. Prefer `static inline` to function-like macros.
- No `malloc`/`free`: allocate statically.
- Keep ISRs minimal (set flags, copy data) and defer the work to the main loop.
- Check HAL/BSP return values and call `Error_Handler()` on failure, matching the generated code.
- Prefer DMA over blocking transfers for ADC, UART and SPI.
